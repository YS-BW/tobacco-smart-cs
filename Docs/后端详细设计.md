# 后端详细设计

## 一、整体代码逻辑流程

### 1.1 对话请求主流程

```
POST /api/chat (session_id, message)
│
├─ 1. 从 SQLite 加载该 session 的历史消息
│
├─ 2. 检查是否有压缩摘要
│     └─ 有 → 注入到 system prompt
│
├─ 3. 取最近 N 轮完整对话（N=15，有压缩摘要时从压缩点之后取）
│
├─ 4. RAG 检索（详见 RAG设计文档.md）
│     ├─ 向量粗筛 Top-20 → Reranker 精排 Top-5
│     └─ 立即推送 references 帧给前端（title, filename, content）
│
├─ 5. 组装 prompt（一个 system message + 对话历史 + 当前问题）
│     ├─ system: 角色设定 + RAG知识库内容 + 压缩摘要
│     ├─ 历史对话（user/assistant 交替，最近15轮）
│     └─ user: 当前问题（干净的用户原话）
│
├─ 6. 调用 Mimo-v2.5（SSE 流式）
│     ├─ reasoning_content → 前端展示思考过程（可选）
│     └─ content → 前端展示最终答案
│
├─ 7. 存入 SQLite（user 消息 + assistant 消息 + references JSON）
│
├─ 8. 记录 qa_logs（用于统计）
│
└─ 9. 检查是否触发压缩（第 15 轮）
      └─ 是 → asyncio.create_task 后台压缩
```

### 1.2 上下文压缩机制

#### 1.2.1 触发条件

```
触发时机：当前会话的 assistant 回复完成后，检查 message_count
触发条件：message_count % 15 == 0（第15、30、45...轮回复完成后）
```

#### 1.2.2 压缩什么

压缩的是**最老的一批未被压缩的消息**，不是全部历史。

```
会话刚开始（1-15轮）：无压缩
第15轮回复完成后：压缩第1-15轮 → 得到摘要A
第16-29轮：正常使用，prompt = 摘要A + 第16-29轮完整对话
第30轮回复完成后：压缩第16-30轮 → 得到摘要B
第31轮起：prompt = 摘要A + 摘要B + 第31轮起的完整对话
第45轮回复完成后：压缩第31-45轮 → 得到摘要C
...
```

#### 1.2.3 上下文组装方式

```python
messages = [
    {
        "role": "system",    # 唯一一个 system message，内部按区块组织
        "content":
            "[角色设定]\n你是烟草行业智能客服助手...\n\n"
            "[知识库检索结果]\n文档1: ...\n文档2: ...\n\n"
            "[上下文摘要]\n第1-15轮: 1. 用户问了焦油量...\n第16-30轮: ..."
    },
    {"role": "user", "content": "第N-14轮问题"},       # 对话历史
    {"role": "assistant", "content": "第N-14轮回答"},
    ...
    {"role": "user", "content": "当前问题"}             # 干净的用户原话
]
```

**一个 system message，对话历史用标准 user/assistant 交替。**

**最近完整对话的窗口大小：**
- 无压缩摘要时：保留最近 15 轮
- 有压缩摘要时：保留最近 15 轮（从最新消息往前取）
- 所以 prompt 中最多出现：所有历史摘要 + 最近 15 轮完整对话

#### 1.2.4 压缩 Prompt

```
请将以下多轮对话压缩为话题摘要列表。

要求：
1. 每轮对话（一问一答）压缩为一个话题
2. 每个话题不超过50个字
3. 保留关键信息：用户问了什么、得到了什么关键结论/数据
4. 按对话顺序输出
5. 严格输出JSON数组，不要输出其他内容

对话内容：
第1轮：
User: {msg}
Assistant: {msg}

第2轮：
User: {msg}
Assistant: {msg}

...

第15轮：
User: {msg}
Assistant: {msg}

输出格式（严格JSON数组）：
["话题1摘要", "话题2摘要", ...]
```

#### 1.2.5 异步压缩时序

```
第15轮用户提问
    │
    ▼
RAG检索 → 推送references → LLM生成回复 → 推送给前端
    │
    ▼
存入SQLite（messages表）
    │
    ├──→ 正常返回给前端（用户看到完整回复）
    │
    └──→ asyncio.create_task(compress(session_id, 1, 15))
         │                                    ↑ 后台异步执行
         │
         ├─ 调用 Mimo-v2.5 压缩（约2-5秒）
         ├─ 解析返回的JSON数组
         ├─ 存入 session_compressions 表（status=done）
         └─ 完成

第16轮用户提问
    │
    ▼
构建prompt时：
    ├─ 查询 session_compressions WHERE session_id=? AND status='done'
    ├─ 找到摘要（1-15轮）→ 注入system prompt
    └─ 取第16轮起的完整对话
```

#### 1.2.6 关键问题：压缩未完成时怎么办

如果用户在第15轮回复后立刻发第16轮消息，压缩可能还没完成：

```
第15轮回复 → 触发压缩（后台进行，需要2-5秒）
用户立刻发第16轮（压缩还没完成）
    │
    ▼
构建prompt时：
    ├─ 查询压缩表 → 没有已完成的压缩
    └─ fallback：直接用最近15轮完整对话（第2-16轮）
       不影响正常使用，只是这轮没有摘要注入

等压缩完成后（比如第17轮时）：
    ├─ 查询压缩表 → 找到摘要（1-15轮，status=done）
    └─ 正常注入摘要 + 取第16-17轮完整对话
```

**结论：压缩未完成不影响正常对话，只是暂时没有摘要注入，用完整对话兜底。**

#### 1.2.7 多次压缩的累积

```
session_compressions 表数据：
┌──────────────────────────────────────────────────┐
│ session_id │ round_range │ compressed_topics      │
├──────────────────────────────────────────────────┤
│ abc-123    │ 1-15        │ ["话题1","话题2",...]   │
│ abc-123    │ 16-30       │ ["话题1","话题2",...]   │
│ abc-123    │ 31-45       │ ["话题1","话题2",...]   │
└──────────────────────────────────────────────────┘

构建prompt时：
    SELECT * FROM session_compressions
    WHERE session_id = ? AND status = 'done'
    ORDER BY round_range

    → 拿到所有已完成的压缩摘要，按顺序拼接
    → 再拼上最近15轮完整对话
```

#### 1.2.8 压缩状态表设计

```sql
CREATE TABLE session_compressions (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    session_id TEXT NOT NULL,
    compressed_topics TEXT NOT NULL,       -- JSON: ["话题1", "话题2", ...]
    round_start INTEGER NOT NULL,          -- 起始轮次（如 1）
    round_end INTEGER NOT NULL,            -- 结束轮次（如 15）
    status TEXT DEFAULT 'pending'          -- pending / done / failed
        CHECK(status IN ('pending', 'done', 'failed')),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (session_id) REFERENCES sessions(id) ON DELETE CASCADE
);
```

**status 说明：**
- `pending`：压缩任务已提交，正在执行
- `done`：压缩完成，摘要可注入 prompt
- `failed`：压缩失败（模型调用异常等），不影响正常对话

#### 1.2.9 完整时序图

```
轮次   用户动作           系统行为                              上下文组成
─────────────────────────────────────────────────────────────────────────────
1      发送消息           正常对话，message_count=1             [1轮对话]
2      发送消息           正常对话，message_count=2             [2轮对话]
...    ...                ...                                    ...
15     发送消息           正常对话，message_count=15            [15轮对话]
                         回复完成后 → 触发压缩(1-15)后台进行
16     发送消息           检查压缩 → 如果done：                  [摘要(1-15)] + [第16轮]
                                 → 如果pending：               [第2-16轮对话]（fallback）
17     发送消息           检查压缩 → 大概率done了                [摘要(1-15)] + [第16-17轮]
...    ...                ...                                    ...
30     发送消息           正常对话，message_count=30
                         回复完成后 → 触发压缩(16-30)后台进行
31     发送消息           [摘要(1-15)] + [摘要(16-30)] + [第31轮]
...    ...                ...                                    ...
45     发送消息           触发压缩(31-45)
46     发送消息           [摘要(1-15)] + [摘要(16-30)] + [摘要(31-45)] + [第46轮]
```

### 1.3 知识库构建流程

```
上传文档
│
├─ 1. 保存原始文件到 data/raw/
│
├─ 2. MinerU 解析 → Markdown
│     ├─ PDF/Word/图片 → 调用 MinerU Standard API
│     └─ Markdown → 直接使用
│
├─ 3. 保存 Markdown 到 data/processed/
│
├─ 4. LangChain 分块
│     ├─ RecursiveCharacterTextSplitter
│     ├─ chunk_size=500, chunk_overlap=50
│     └─ 按标题/段落切分
│
├─ 5. bge-large-zh-v1.5 生成 embedding
│
├─ 6. 存入 ChromaDB collection "knowledge_base"
│     metadata: {source: filename, chunk_index: i}
│
└─ 7. 更新 knowledge_docs 表状态为 "ready"
```

## 二、数据结构

### 2.1 SQLite 表结构

```sql
-- 会话表
CREATE TABLE sessions (
    id TEXT PRIMARY KEY,                              -- UUID
    title TEXT NOT NULL DEFAULT '新对话',              -- 首条用户消息截取前20字
    message_count INTEGER DEFAULT 0,                  -- 消息轮次计数
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- 消息表
CREATE TABLE messages (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    session_id TEXT NOT NULL,
    role TEXT NOT NULL CHECK(role IN ('user', 'assistant')),
    content TEXT NOT NULL,
    reasoning_content TEXT,                            -- 推理过程（仅 assistant）
    references TEXT,                                   -- 引用来源 JSON（仅 assistant）
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (session_id) REFERENCES sessions(id) ON DELETE CASCADE
);

-- 压缩摘要表
CREATE TABLE session_compressions (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    session_id TEXT NOT NULL,
    compressed_topics TEXT NOT NULL,                   -- JSON: ["话题1", "话题2", ...]
    round_start INTEGER NOT NULL,                      -- 起始轮次（如 1）
    round_end INTEGER NOT NULL,                        -- 结束轮次（如 15）
    status TEXT DEFAULT 'pending'                      -- pending/done/failed
        CHECK(status IN ('pending', 'done', 'failed')),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (session_id) REFERENCES sessions(id) ON DELETE CASCADE
);

-- 问答日志（统计用）
CREATE TABLE qa_logs (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    session_id TEXT NOT NULL,
    user_question TEXT NOT NULL,
    retrieved_doc_ids TEXT,                            -- JSON: 命中的文档chunk id列表
    max_similarity REAL,                               -- 最高相似度分数
    kb_hit INTEGER DEFAULT 0,                          -- 1=命中 0=未命中
    response_time_ms INTEGER,                          -- 响应耗时
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (session_id) REFERENCES sessions(id) ON DELETE CASCADE
);

-- 知识库文档记录
CREATE TABLE knowledge_docs (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    filename TEXT NOT NULL,
    file_type TEXT NOT NULL,                           -- pdf/word/image/markdown
    chunk_count INTEGER DEFAULT 0,
    status TEXT DEFAULT 'processing' CHECK(status IN ('processing', 'ready', 'failed')),
    error_msg TEXT,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

### 2.2 Pydantic 模型

```python
# --- 请求模型 ---

class ChatRequest(BaseModel):
    session_id: str
    message: str

class SessionCreate(BaseModel):
    title: str | None = None        # 可选，不传则自动生成

class KnowledgeUpload(BaseModel):
    files: list[UploadFile]

# --- 响应模型 ---

class SourceInfo(BaseModel):          # 引用来源
    index: int                        # 编号 [1] [2] [3]
    title: str                        # 文档标题（取 heading_path 最后一级）
    filename: str                     # 源文件名
    content: str                      # 命中的子块内容（截取前200字）

class ChatChunk(BaseModel):          # SSE 流式返回的每一帧
    type: Literal["reasoning", "content", "references", "done"]
    text: str = ""
    sources: list[SourceInfo] | None = None  # 仅 type=references 时有值

class SessionInfo(BaseModel):
    id: str
    title: str
    message_count: int
    created_at: str
    updated_at: str

class MessageInfo(BaseModel):
    id: int
    role: str
    content: str
    reasoning_content: str | None
    references: list[SourceInfo] | None   # 仅 assistant 消息有值
    created_at: str

class KnowledgeDocInfo(BaseModel):
    id: int
    filename: str
    file_type: str
    chunk_count: int
    status: str
    created_at: str

class StatsOverview(BaseModel):
    total_sessions: int
    total_messages: int
    total_docs: int
    kb_hit_rate: float              # 知识库命中率百分比

class TopQuestion(BaseModel):
    question: str
    count: int
```

## 三、API 详细设计

### 3.1 对话 API

#### `POST /api/chat` — 发送消息（SSE 流式）

```
请求：
{
    "session_id": "uuid-xxx",
    "message": "黄鹤楼硬蓝的焦油量是多少？"
}

响应：text/event-stream
data: {"type": "references", "sources": [           ← RAG 检索完成后立即推送
    {"index": 1, "title": "黄鹤楼产品参数表", "filename": "huanghelou.pdf", "content": "焦油量：10mg..."},
    {"index": 2, "title": "卷烟分类标准", "filename": "classification.md", "content": "烤烟型卷烟是指..."}
]}
data: {"type": "reasoning", "text": "用户询问..."}   ← LLM 开始生成
data: {"type": "reasoning", "text": "让我检索..."}
data: {"type": "content", "text": "根据"}
data: {"type": "content", "text": "知识库"}
data: {"type": "content", "text": "信息..."}
data: {"type": "done", "text": ""}
```

**逻辑：**
1. 存用户消息到 messages 表
2. 加载历史 + 压缩摘要
3. RAG 检索 → 向量粗筛 Top-20 → Reranker 精排 Top-5
4. **立即推送 references 帧**（title、filename、content）给前端
5. 组装 prompt，调 Mimo-v2.5 stream
6. 逐 chunk 推 SSE（reasoning / content）给前端
7. 完整回复存 messages 表（含 references JSON）
8. 记录 qa_logs（含命中的 doc_id 列表）
9. 检查是否触发压缩

#### `POST /api/knowledge/upload` — 上传文档

```
请求：multipart/form-data

响应：

    "message": "3 个文件已提交处理",
```
